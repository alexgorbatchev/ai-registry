# AI Assistant Guidelines for `ai-registry`

This repository is a central registry for AI skills, commands, rules, and harness configuration. As an AI assistant working in this repository, you must adhere to the following rules:

## Purpose
This repository manages reusable AI skills and commands plus the harness configuration that ships them. It serves as the single source of truth for the shared system prompt, generated harness outputs, and setup workflow.

The registry is maintained interactively with agent assistance. Reusable guidance may support unattended workflows in other repositories; registry maintenance does not itself require an unattended workflow.

## File Conventions
- **Reusable Assets**:
  - **Skill Authoring Guidance**: Follow `skills/AGENTS.md`. Use `prompt-writer` whenever generating, writing, or revising AI agent instructions; `skill-writer` adds skill-bundle conventions and validation, while `docs-writer` owns project documentation structure and maintenance. Review AI agent instructions with concrete acceptance checks and bounded review rounds rather than numerical quality scores. Generic skills must contain no harness-specific instructions; place those under `harnesses/<target>/skills/` instead.
  - **Bundled Skill Dependencies**: Register skill packages needed by repository-wide typechecking as root Bun workspaces, including `skills/user/disk-cleanup`, so normal installs cover their dependencies. Exclude installed dependencies, local lockfiles, and scratch directories from generated skill copies through `.registry-ignore`.
  - **Skills (`skills/`)**: Skills are grouped into `skills/agent/` for agent-runnable skills and `skills/user/` for user-invokable skills. Each skill resides in its own isolated folder and contains at least a `SKILL.md` file detailing the domain knowledge, workflows, and rules. User skills in `skills/user/` do not contain `disable-model-invocation: true` in their source `SKILL.md`; the build/bootstrap process automatically injects it into generated harness outputs. In generated outputs, skills from `agent/` and `user/` are merged flat into `skills/`.
  - **Commands (`commands/`)**: Slash commands and reusable task prompts belong here.
  - **GitHub Issue Workflow**: Issue authoring, implementation, review, integration, and historical issue-merge repair live in the `github-issues` skill in the private overlay. Do not recreate them here.
  - **Pull Requests**: Maintain PR-writing and PR review-feedback guidance in `skills/agent/github-pr/`, with one bundled reference per mode, not a duplicate command. PR descriptions, comments, and replies posted from the user's account use the account owner's first-person voice (`I`, `me`, `my`), including approval and landing notices. Do not refer to that account owner as `the user` or narrate an assistant intermediary. Ground actions, results, and approvals in actual work and authorization; separate bot reviews speak for the bot's identity. Keep titles concise and avoid drawn-out explanations. Cover related issues from commit messages, the problem and motivation, change type, tests, and risks. When a PR from an external author (not `OWNER`, `MEMBER`, or `COLLABORATOR`) is merged, closed, or superseded, thank the author on that PR and say where the work landed.
  - **System (`system/`)**: Shared repo-level instruction fragments and memory guidance belong here. `system/system.md` is the shared system prompt every harness ships: Codex as `AGENTS.md`, Pi as `APPEND_SYSTEM.md`, Claude Code as `CLAUDE.md`, and OpenCode through `instructions` in `harnesses/opencode/opencode.jsonc`.
  - **Self-Contained Logic**: Keep skills and commands self-contained; do not assume other skills are present. Matt Pocock's explicitly user-invoked workflows may depend on other bundled user skills; maintain their required dependencies. Keep all skills authored by `mattpocock` under `skills/user/`, as specified in `skills/AGENTS.md`.
- **The Harnesses (`harnesses/`)**:
  - Global configuration overrides for specific tools (e.g., `harnesses/opencode/opencode.jsonc`).
  - Unified harnesses can also provide repo-local build plugins at `packages/registry-cli/src/harnesses/<target>/build.ts`; `packages/registry-cli/src/commands/buildCommand.ts` statically imports those plugins.
  - When a task says to change OpenCode config "in ai-registry", edit the checked-in source file under `harnesses/opencode/`, not the machine-local installed config under `~/.config/opencode/`.
  - The checked-in OpenCode docs snapshot lives under `harnesses/opencode/docs/`; refresh it with `bun run sync:opencode-docs`, which runs `packages/registry-cli/src/bin/sync-opencode-docs.ts`.
  - Repository-local harness maintenance guidance belongs in `harnesses/AGENTS.md`.
  - Each harness contains a `fetch-source.sh` script to clone or update its upstream source code into a local, git-ignored scratch folder at `harnesses/<harness>/.tmp/<harness>-source/` for reference and inspection. These scripts and folders are omitted from the generated harness outputs using `.registry-ignore`.
  - **USE SOURCE REFERENCE FIRST:** When diagnosing harness-specific issues, analyzing behavioral contracts, or updating configurations, ALWAYS consult the local checked-out source code under `harnesses/<harness>/.tmp/<harness>-source/` first. Never guess, assume, or rely on memory. Run the respective `fetch-source.sh` first if the directory is absent.
  - Only files inside `harnesses/<target>/` are injected directly into the matching target output directories during the build process, subject to `.registry-ignore` rules.
  - Current generated harnesses are OpenCode (`harnesses/opencode/`), Codex (`harnesses/codex/`), Pi (`harnesses/pi/`), and Claude Code (`harnesses/claude-code/`).
- **Standalone Packages (`packages/<package-name>/`)**:
  - Publishable repo-local packages that are distributed independently from generated harness outputs live under `packages/`.
  - Add each standalone package to the root `package.json` workspaces so `bun install` manages it consistently.
  - Package-local guidance belongs in `packages/<package-name>/AGENTS.md` when a package has non-obvious contracts or validation rules. For the template resolver package, see `packages/template-resolver/AGENTS.md`.
- **Vendored Packages (`vendor/`)**:
  - Third-party code packages that need to live in this repo as Bun workspaces belong here.
  - Use this for repo-local harness dependencies such as file-based OpenCode plugins with runtime imports.
  - Vendored packages are repo-local runtime dependencies, not generated-output surfaces; reference them from source configs with `file://<%- repo_root %>/...` when needed, or symlink single files into generated roots from the harness build plugin.
  - Record the upstream repository, pinned commit, and file checksum in the vendored package's `README.md` so the copy stays reproducible.
- **External Skill Lock (`skills-lock.json`)**:
  - Records third-party skills vendored into `skills/` via the Skills CLI.
  - Commit it whenever you add or update external skills.

## Architecture & Build Process
This repository uses a custom build script (`packages/registry-cli/src/commands/buildCommand.ts` via `bun run build`) to locally compile the registry into ready-to-use configurations for harnesses directly from the checked-in source tree.
- **Unified Outputs:** The script generates final harness outputs in `.output/`. It writes one root per harness: `.output/opencode`, `.output/codex`, `.output/pi`, and `.output/claude-code`. Every harness ships every registry skill and command. Generated harness skills are merged flat from `skills/agent/`, `skills/user/`, overlay `skills/`, or `harnesses/<target>/skills/`, with build-time template tags resolved and `disable-model-invocation: true` automatically injected for user skills. Skills that are not authored by `alexgorbatchev` are emitted with their author prefix as `<author>-<skill>` in both directory name and frontmatter `name` across all harness outputs. They are copies rather than symbolic links so that EJS tags inside `SKILL.md` and bundled skill files reach the agent resolved; edits made to a generated skill are recovered through the generated-output drift and sync-back flow instead of writing straight through a link.
- **Harness Skill Override Precedence:** Harness-specific skills under `harnesses/<target>/skills/` (grouped into `agent/` and `user/`) take precedence over global skills (`skills/` and overlay `skills/`) on name collision across all four harnesses (OpenCode, Codex, Pi, and Claude Code). When a collision occurs, the harness-specific skill cleanly overrides the global skill in the generated output for that harness target.
- **Hostname Skill Variants:** Keep a default `SKILL.md` in each skill bundle. The build selects `variants/<hostname>/SKILL.md` within the resolved bundle using the OS hostname or `AI_REGISTRY_HOSTNAME`, with exact case-sensitive matching and default fallback when no matching directory exists. Hostnames start with a letter or digit and contain only letters, digits, dots, underscores, or hyphens; empty or invalid overrides fail. Matching variants must contain a regular `SKILL.md`, valid YAML frontmatter, a non-empty description and body, and the same name and author as the default. Selection follows existing overlay and harness precedence, applies to reusable and harness-local skills, and changes only the emitted root `SKILL.md`. Shared resources come from the bundle root; exclude its entire `variants/` directory from generated output. Keep actual private hostnames and environment instructions in the private overlay, which replaces whole bundles. Preserve the selected source mapping through template rendering and output assembly; `file_path` and `file_dir` refer to the selected variant's original path. The manifest records skill source paths, and sync-back rejects recovery when the recorded source differs from the current selection. Edit include-based skills at their source because sync-back does not reconstruct include directives.
- **Harness Plugins:** A harness can keep target-specific output shaping in `packages/registry-cli/src/harnesses/<target>/build.ts`. The root build resolves every registry skill and command once, then calls each plugin's `buildOutput` hook to write that harness's root under the staging directory.
- **No Top-Level Harness Code:** The top-level scripts (`packages/registry-cli/src/commands/buildCommand.ts` and `packages/registry-cli/src/commands/bootstrapCommand.ts`) MUST NOT contain any harness-specific generation logic, hardcoded template paths, or target-specific helper script generation. All such logic must live exclusively within the respective harness plugin (`packages/registry-cli/src/harnesses/<target>/build.ts`).
- **Generated Output Manifest:** Each successful unified build writes `.output/manifest.json` with managed files, directories, symlinks, mapped source paths, and source fingerprints. Treat harness-written changes in generated files as expected. During bootstrap, preserve session and runtime data and automatically recover supported generated-file edits into their mapped source when doing so will not overwrite source changes. Regenerate after successful recovery. If source and generated edits conflict, recovery is unsupported, or saving an edit fails, preserve both versions and suspend dependent output application with the exact conflict reported. Do not request confirmation merely because a harness changed a generated file. Recovery requires verified generated and source baselines and an exact reversal of supported transformations; includes, expressions, and control flow require source edits. Existing drift without source fingerprints must be reconciled into source before establishing a fresh baseline. Unmanaged harness-owned files are preserved. `-y` does not bypass recovery or conflict checks.
- **Harness Homes:** Harness runtime state (sessions, transcripts, history, databases, logs, installed plugins, credentials) never lives under `.output/`, so deleting `.output/` or moving the checkout cannot hide or split it. Each harness home is a real directory outside the repository: `${CLAUDE_CONFIG_DIR:-~/.claude}`, `${CODEX_HOME:-~/.codex}`, `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, and the OpenCode config directory. Bootstrap symlinks into each home only the top-level entries `.output/manifest.json` records for that harness output (managed entries plus `syncedFilePaths`); everything else in the home is harness-owned and left in place. Bootstrap repoints managed links that target another checkout, backs up a real entry occupying a managed name as `<name>.backup-<timestamp>`, removes dangling links into the harness output, and refuses a home that is still a symlink. Harness plugins create no runtime directories in generated output.
- **Synced Settings Files:** Settings files a harness edits at runtime (Claude Code `settings.json`, Pi `settings.json`, OpenCode `opencode.jsonc`, Codex `config.toml`) are regular files in the generated output, never symlinks; harness homes reach them through bootstrap's managed links, and the manifest lists them under `syncedFilePaths`; the sync replaces a symlink left by an earlier layout with a copy of its target. They are registered through `buildSupport.syncSettingsFile(...)` in the harness plugin. They are excluded from `manifest.json` and never reported as drift. After the managed outputs sync, the build merges each key three ways: the live file, the newly rendered source, and the previous build's merged settings recorded under `.tmp/settings-sync/`. Harness-made additions, changes, and removals are written back to the registry source with repository paths reversed into template tags; source changes are applied to the live file; JSON, JSONC, and TOML are edited in place so comments and key order survive. When both sides changed the same value, lists combine both sides' edits, nested objects merge per key, and other values keep the source version with a printed warning. Without a recorded base, both sides are combined and the live value wins disagreements. Live-only key patterns (`*` matches any key) never reach the source: values a harness stamps on its own (Pi `lastChangelogVersion` and `extensionChangelogVersions`, Codex `notice` and `tui.model_availability_nux`), entries keyed by or pointing at local paths (each Codex `projects` entry, `skills.config`, and `hooks.state`; Codex and ChatGPT desktop app entries that point at machine-local binaries and caches: `notify`, `marketplaces.openai-bundled`, `marketplaces.openai-primary-runtime`, `mcp_servers.node_repl` (except registry entries in `env.NODE_REPL_TRUSTED_SERVICES`, merged into its JSON object after live-only preservation while retaining app-added services), and `mcp_servers.cua_repl`), and fields that can hold credentials (OpenCode `mcp.*.headers` and `mcp.*.environment`, Codex `mcp_servers.*.env` and `mcp_servers.*.http_headers`). Source files that were tracked and clean before the sync are committed as `chore(settings): sync harness settings` with `git commit --only`, leaving other staged work alone; files that already had uncommitted edits keep the synced change uncommitted with a warning. Scheduled updates disable settings auto-commit with `AI_REGISTRY_SETTINGS_AUTO_COMMIT=0` and leave synced edits uncommitted; they push only existing outgoing commits.
- **Source Tree Ignores:** When the build stages files from `skills/`, `commands/`, and `harnesses/<target>/`, it honors nested `.registry-ignore` files with `.gitignore`-style matching so repo-local scratch files can stay out of generated outputs.
- **Script Layout:** Executable repo entrypoints stay directly under `packages/registry-cli/src/bin/` and use dash-based filenames. TypeScript helpers that are imported by other scripts and are not meant to be run directly belong under `packages/registry-cli/src/lib/`.
- **Public CLI Helpers:** Any wrapper script intended for `~/.local/bin/` symlinking (for example `air-*`, `claude-*`, `codex-*`, or `pi-*`) MUST NOT be checked into `packages/registry-cli/src/bin/`. Instead, `packages/registry-cli/src/commands/buildCommand.ts` must generate them into `.output/bin/` during the build process, and `packages/registry-cli/src/commands/bootstrapCommand.ts` will symlink them from there.
- **Bootstrap Command:** `bun run bootstrap` is the repo-local setup entrypoint. It installs dependencies, builds the generated outputs, applies the generated OpenCode config to an XDG-style home unless `OPENCODE_CONFIG_DIR` is set, applies `.output/codex` to `${CODEX_HOME:-~/.codex}`, `.output/pi` to `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, and `.output/claude-code` to `${CLAUDE_CONFIG_DIR:-~/.claude}`, and always refreshes the generated public wrappers in `~/.local/bin`, removing broken links to wrappers the build no longer generates. Applying an output follows the Harness Homes rules.
- **Scheduled Updates:** `bun run scheduled:update` runs the repo-local `packages/registry-cli/src/bin/scheduled-update.ts` entrypoint. It creates `.tmp`, appends worker output to `.tmp/scheduled-update.log` with a local timestamp formatted as `[YYYY-MM-DD HH:MM]` on each line, and serializes manual and scheduled runs with macOS `lockf` or Linux `flock`, skipping overlaps. Each run prunes log entries older than 48 hours at minute precision and entries without the supported timestamp format. Its internal logger holds the native lock through pruning, worker execution, and all log writes. Its internal worker pulls the current branch's upstream with rebase and invokes bootstrap with `-y` on every run, so the build also syncs settings the harnesses changed locally without creating commits, even when nothing arrives. A checkout with staged, unstaged, or untracked changes skips the pull and push and still bootstraps, so harness settings keep syncing; never stash or rewrite uncommitted work, because restoring it can conflict and rewriting its files resets the commit sweep's quiet window. A failed rebase rolls back HEAD. Hooks are suppressed during the update and rollback to avoid duplicate bootstrap execution. `.tmp/scheduled-update-recovery.json` blocks retries after interruption or failed recovery; inspect its saved HEAD and finish recovery before removing it. After a successful pull and bootstrap, it pushes outgoing commits only to the current branch's upstream without force or tags, including runs with no incoming changes. A failed bootstrap skips the push; push failures preserve commits for the next run to retry. Push hooks remain enabled, and GitHub pushes check outgoing messages and patches for restricted private domains.
- **Secret Scanning:** The checked-in `.githooks/pre-push` hook delegates to `packages/registry-cli/src/bin/scan-pushed-commits.ts`, which runs `gitleaks git` over every commit a push would publish (new history on updated branches, everything not on the remote for new branches) and blocks the push on findings. A missing or failing `gitleaks` blocks the push instead of passing it. When settings auto-commit is enabled, the settings sync scans each clean synced source file with `gitleaks dir` and leaves a change with findings uncommitted. Record reviewed false positives in `.gitleaksignore`. Schedulers invoke the entrypoint directly without wrapping it in another lock.
- **Codex Harness Mapping:** The Codex harness writes `system/system.md` to `AGENTS.md`, renders `harnesses/codex/config.toml` into `config.toml` as a synced settings file, copies `harnesses/codex/rules/`, and stages registry and Codex-only skills under `skills/`. It packages every registry command as a native skill bundle in `skills/`, preserving command content as `SKILL.md` and setting `policy.allow_implicit_invocation: false` in `agents/openai.yaml`. Commands require YAML frontmatter with a non-empty `description`. An explicit frontmatter `name` determines the skill name; otherwise names use `command-<filename>` with leading hyphens removed and repeated hyphens collapsed. Names must be lowercase kebab-case and at most 64 characters; duplicate command names and collisions with staged skills fail the build. Invoke these workflows with `$<skill-name>` or `/skills`. Codex outputs have no managed `prompts/` directory. Runtime files such as `auth.json` remain Codex-owned under `CODEX_HOME`. No `codex` wrapper is generated.
- **Codex Project Trust (`AI_REGISTRY_CODEX_TRUSTED_DIRS`):** Codex matches project trust by exact checkout path, so a trusted parent folder covers nothing beneath it. Read a PATH-style list of folders (home and registry-relative paths expand; missing paths warn and are skipped) and trust every git checkout found beneath them: every repository outside checkouts, skipping hidden folders, `node_modules`, and symlinks, plus the submodules each checkout declares in `.gitmodules`. Write the entries into the generated Codex `config.toml` only; `projects` entries are live-only, so they never reach the registry source, and an entry Codex already records, including `untrusted`, keeps its live value.
- **Smoke Test:** `bun run bootstrap:smoke` validates the bootstrap flow against `.tmp/bootstrap-smoke/`, treating that directory as a fake `HOME` with the repo staged at `development/ai-registry`.
- **Pi Harness Mapping:** The Pi harness writes `system/system.md` to `APPEND_SYSTEM.md`, maps registry commands plus `harnesses/pi/prompts/` to `prompts/` (a name collision fails the build), stages registry and Pi-only skills under `skills/`, copies `settings.json` as a synced settings file, and copies `models.json`, `web-search.json`, and `extensions/` when `harnesses/pi/` ships them. Bootstrap also links `web-search.json` to `~/.pi/web-search.json`. The output `bin/` directory contains the `pi-install`, `pi-update`, and `pi-uninstall` helpers. No `pi` wrapper is generated, because the real `pi` binary already reads `${PI_CODING_AGENT_DIR:-~/.pi/agent}`.
- **Claude Code Harness Mapping:** The Claude Code harness writes `system/system.md` to `CLAUDE.md`, maps registry commands to `commands/`, stages registry and Claude Code-only skills under `skills/`, and copies every file shipped under `harnesses/claude-code/` except `skills/` into the output root. No `claude` wrapper is generated, because the real `claude` binary already reads `~/.claude`. It generates the `cll` helper for launching Claude Code through an on-prem or remote LiteLLM proxy.
- **OpenCode Harness Mapping:** The OpenCode harness copies `harnesses/opencode/` into the output root, syncs `opencode.jsonc` as a settings file, merges registry commands into `commands/` (a collision with a harness command fails the build), stages registry and OpenCode-only skills under `skills/`, and generates the `air-opencode-*` helpers. It generates no agents; the shared system prompt reaches OpenCode through `instructions` in `opencode.jsonc`.
- **Generated Output Templates:** Keep source filenames and use native EJS syntax in text files. Use raw output tags such as `<%- repo_root %>`, `<%- file_path %>`, and `<%- file_dir %>`; the latter two identify the original source across nested includes. Use `<%- include("/system/system.md") %>` for repository-root-relative includes and `<%- env("VAR_NAME", "fallback") %>` for environment values with an optional fallback. EJS expressions and control flow are supported. Render each file exactly once; `<%%` emits a literal opening delimiter. Foreign `{{...}}` syntax passes through unchanged. `env()` reads the build's own environment first; a variable it lacks comes from the user's login shell (`shell-env`, `$SHELL -ilc`), started at most once per build and only when a template needs it, so scheduled builds see values that only interactive shell startup files export. Do not render secrets with empty fallbacks: a missing value must fail the build so a scheduled run keeps the last good output instead of writing blanks. Unknown variables, invalid JavaScript, missing includes, and environment values missing from both the build and the login shell without fallbacks fail the build. Resolved includes cannot escape the repository root. Templates execute trusted JavaScript. Generated-edit recovery supports canonical raw path-variable tags; edit other EJS templates at their source.
- **Canonical Path References:** When checked-in guidance or generated text needs a canonical path inside this repository that would otherwise be machine-specific and absolute, use template variables instead of hardcoded absolute paths. Prefer the most specific token available for canonical folders: `<%- skills_dir %>/...`, `<%- commands_dir %>/...`, and `<%- output_dir %>/...`. For canonical folders without a dedicated token, anchor the path from `<%- repo_root %>`, such as `<%- repo_root %>/harnesses/...`, `<%- repo_root %>/system/...`, `<%- repo_root %>/vendor/...`, `<%- repo_root %>/packages/registry-cli/...`, `<%- repo_root %>/README.md`, and `<%- repo_root %>/AGENTS.md`. Use normal repo-relative paths elsewhere in checked-in docs.
- **Private Overlay Registries (`AI_REGISTRY_OVERLAY`):** Read a PATH-style list of external registry directories using the platform path delimiter. Expand home and relative paths, ignore empty entries, warn and skip missing paths, and deduplicate normalized paths by keeping their last occurrence. Merge `skills/` and `commands/` from left to right; the last matching name replaces the whole skill bundle or command. Build and bootstrap print skill conflict notes identifying selected and replaced sources. Preserve harness-specific skill override precedence. The `overlay_dir` template variable identifies the last active overlay; use `file_dir` for resources relative to assets in other overlays.

## Development Workflow
- Automatically record explicit standing user instructions, such as “always do X” or “never do Y,” in the narrowest applicable `AGENTS.md` or existing policy file without requiring a separate request to save them. Update an existing rule in place when the user clearly changes it. Keep one-task directions, progress, handoffs, and session data out of policy files. Ask only when the intended policy scope or resolution of a material conflict is unclear.
- Let models choose search and code-navigation tools according to the task and available capabilities; do not add mandatory tool ordering or tool-specific stop rules.
- Keep dependency investigation and library integration within the authorized task's required capabilities. Follow the shared library guidance in `system/system.md`.
- Apply the shared red/green and test-sensitivity rules to changes in executable behavior; use applicable validators for non-executable changes. Keep sensitivity checks isolated from other actors' changes, following `system/system.md`.
- **Instruction maintenance scope:** Auditing or editing instructions, including committing and merging that work, does not make newly specified but unimplemented enforcement a prerequisite to completing the maintenance task. Record enforcement gaps as follow-up issues and run existing checks applicable to the actual changes. Do not silently expand the task into implementing enforcement infrastructure or remediating repository-wide noncompliance. This does not waive existing failing checks or the testing and coverage requirements for behavior-changing implementation work. A user-deferred generation or application step suspends only that step; continue independent validation and authorized integration, and report the unrun verification without claiming compliance.
- Preserve other actors' changes, index state, locks, and refs. Suspend only conflicting operations and continue independent authorized work in an owned, isolated worktree when safe. Staged-file age does not authorize takeover or a whole-worker halt; record and recheck ownership blockers under `system/system.md`.
- Routine branch and path-scoped index operations needed for an authorized task may proceed in owned worktrees after state and ownership checks. Destructive Git operations require explicit authorization and remain subject to executable guards; command permissions do not establish ownership. Follow the shared guidance in `system/system.md`.
- **CRITICAL ANONYMIZATION RULE:** This registry is designed to be public and reusable. When creating or editing *any* file in this repository (especially skills, commands, prompts, and harness configuration), you MUST strictly anonymize and generalize all potentially Personal Identifiable Information (PII) and proprietary data. This includes, but is not limited to: company names, specific project names, employee names, locations, desk numbers, internal URLs, specific server hostnames, proprietary nomenclature, private API keys, or hardcoded passwords. Exception: the repository's already-public ownership and attribution identifiers may remain when they are required for the published package/repository identity or canonical author metadata (for example the GitHub owner, package scope, or `author` field used by this registry). Do not introduce any other personal details beyond that narrow public-attribution scope. Ensure all other content added to this repository is globally applicable and scrubbed of private context.
- When asked to create a new reusable skill, create a new directory under `skills/agent/` (for agent-runnable skills) or `skills/user/` (for user-invokable skills). For user skills, do not add `disable-model-invocation: true` in the source `SKILL.md`. Keep concerns separated. If a skill should ship only with one harness, place it under that harness's source tree instead.
- When vendoring an external skill, use `bun run skills:add 'npx skills add <source> --skill <name>'`. That wrapper applies `-a openclaw --copy -y` behind the scenes so the skill is copied into the canonical `skills/` directory and tracked in `skills-lock.json`, while maintaining the upstream author in `SKILL.md`.
- When updating vendored external skills, use `bun run skills:update` instead of plain `npx skills update`, because the upstream update command does not preserve the canonical `skills/` target in this repo; the wrapper also preserves and updates upstream authors across refreshes.
- Preserve third-party-authored skill content. Keep local policies in registry-owned guidance and record unresolved upstream findings instead of rewriting those bundles.
- When creating a new command, add it under `commands/`.
- When creating a publishable standalone package, place it under `packages/<package-name>/` and add it to the root Bun workspaces.
- When vendoring a third-party code package for a harness integration, place it under `vendor/` and wire it through the root Bun workspaces instead of placing installable package source inside a generated harness directory.
- After modifying any skill, command, `system/system.md`, harness file, or `skills-lock.json`, ALWAYS run `bun run build` to regenerate the configurations.
- **CRITICAL:** This `AGENTS.md` and the `README.md` must be kept strictly up to date whenever structural or architectural changes are made to this repository. Do not leave documentation stale.
- **Testing & Code Coverage:** For code changes that alter executable behavior, add or update meaningful behavioral tests. `bun run coverage` gates `packages/registry-cli`; its scope and counting rules are in `packages/registry-cli/AGENTS.md`. Require at least 90% line coverage and 90% function coverage across the non-test source of each affected first-party package; include unexecuted source files and exclude `scripts/` directories. Document and configure the coverage command, source scope, metrics, and exclusions. Reproduce a blocking baseline failure on the untouched base and handle the smallest necessary prerequisite repair under the existing policy. Do not weaken coverage gates or make token test edits to satisfy this rule.
- When structural, workflow, or location changes affect how agents should add things to this registry, update `skills/agent/ai-registry-integration/SKILL.md` in the same change so the registry-integration guidance stays accurate.
