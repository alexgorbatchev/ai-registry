# AI Assistant Guidelines for `ai-registry`

This repository is a central registry for AI skills, commands, rules, and agent profiles. As an AI assistant working in this repository, you must adhere to the following rules:

## Purpose
This repository manages reusable AI skills and commands plus the configurations (profiles) that assemble them. It serves as the single source of truth for your agent personas, generated harness outputs, and setup workflow.

The registry is maintained interactively with agent assistance. Reusable guidance may support unattended workflows in other repositories; registry maintenance does not itself require an unattended workflow.

## File Conventions
- **Reusable Assets**:
  - **Skill Authoring Guidance**: Follow `skills/AGENTS.md`. Use `prompt-writer` whenever generating, writing, or revising AI agent instructions; `skill-writer` adds skill-bundle conventions and validation, while `docs-writer` owns project documentation structure and maintenance. Review AI agent instructions with concrete acceptance checks and bounded review rounds rather than numerical quality scores. Generic skills must contain no harness-specific instructions; place those under `harnesses/<target>/skills/` instead.
  - **Bundled Skill Dependencies**: Register skill packages needed by repository-wide typechecking as root Bun workspaces, including `skills/user/disk-cleanup`, so normal installs cover their dependencies. Exclude installed dependencies, local lockfiles, and scratch directories from generated skill copies through `.registry-ignore`.
  - **Skills (`skills/`)**: Skills are grouped into `skills/agent/` for agent-runnable skills and `skills/user/` for user-invokable skills. Each skill resides in its own isolated folder and contains at least a `SKILL.md` file detailing the domain knowledge, workflows, and rules. User skills in `skills/user/` do not contain `disable-model-invocation: true` in their source `SKILL.md`; the build/bootstrap process automatically injects it into generated harness outputs. In generated outputs, skills from `agent/` and `user/` are merged flat into `skills/`.
  - **Commands (`commands/`)**: Slash commands and reusable task prompts belong here.
  - **GitHub Issue Workflow**: Maintain issue authoring, one active issue at a time through merge and cleanup, and explicit historical issue-merge repair in `skills/agent/github-fix-issues/`. Select by verified priority labels, highest first, then oldest creation time within each group; without priority labels use oldest first. Resolve prerequisites before dependents. A verified blocker suspends only the affected issue and its dependents; record its evidence, unblock condition, and resume state, preserve its artifacts, and continue the next independent issue within the authorized queue. Recheck blocked work at selection boundaries before restoring eligibility; do not preempt a progressing active issue. Keep this skill harness-independent; do not recreate issue-specific commands, separate issue skills, or harness overrides of it. Its bundled references own queue persistence, sequential scheduling, CI gates, reviewer identity, fast-forward integration, and cleanup rules.
    PR descriptions reference their issues and carry concise testing summaries. Watch CI until green before bot review; fix failures or review findings and repeat CI/review until approved, then merge and clean up before selecting another issue unless a verified blocker requires suspension. Pending CI or a running reviewer alone does not justify suspension. CI is the completion record; do not publish log transcripts, evidence bundles, or round manifests. Reviewer operating instructions belong in the installed skill. Clean reviews submit only native approval without a body, comments, or summary; reviewer prose is limited to actionable findings.
    Completion reports give concise verified check results and material limitations, with native CI links or existing local log paths where applicable. Retain raw logs in the execution system; local logs do not replace required CI.
    Existing task authorization covers the smallest same-repository baseline repair needed to unblock required checks, verified on the untouched base, in its own prerequisite ticket and change set through the same checks, review, and integration gates. Honor explicit exclusions and other owners' changes. Compatibility layers require explicit authorization; migration approval alone does not grant it. An authorized temporary layer must include removal and verification.
  - **Reviewer Helper**: Keep bot access automation in that skill's `scripts/reviewer.ts` bundle. Its private dependency manifest is a root workspace so normal installs cover typechecking and tests; the root justfile exposes its development recipes as `reviewer`. Update its skill interface and setup reference in the same change as commands, flags, defaults, environment settings, output, or side effects. Keep personal bot identities and token-variable names in local configuration, and exclude installed dependencies and tests from generated skill copies.
  - **Issue Requirement Recovery**: Recover acceptance criteria from verified issue discussion, specifications, tests, and documented behavior; a missing structured acceptance section alone is not a blocker, and current behavior or tests alone do not establish the desired change. Resolve priority ambiguity from verified repository guidance. If material requirements or label ranks remain unresolved, record the question and unblock condition, suspend only affected issues and dependents, and continue independent authorized work. Do not invent product behavior or ranks, or alter labels to bypass ambiguity.
  - **Issue CI Recovery**: Inspect applicable CI workflows, trigger conditions, and access before implementation. Follow `skills/agent/github-fix-issues/references/checks-and-ci.md` for readiness, bounded prerequisite repairs, failure classification, and infrastructure retry policy. Persist retry state across restarts; pending CI or review does not consume infrastructure attempts. Exhausted retries with continuing infrastructure-failure evidence suspend only dependent work; never waive checks.
  - **Issue Setup Readiness**: Before implementation, follow `skills/agent/github-fix-issues/references/setup.md` to check tools, repository/remote identity, implementer authentication, configured distinct reviewer and token availability, access, and protection compatibility. The workflow uses `main`; never silently substitute another branch. Persist non-secret findings and exact missing requirements, suspend only dependent actions, and recheck before resuming and at review/integration gates. Preserve prepared work, credentials, default authentication, and protections; do not escalate existing permissions.
  - **Pull Requests**: Maintain PR-writing and PR review-feedback guidance in `skills/agent/github-pr/`, with one bundled reference per mode, not a duplicate command. PR descriptions, comments, and replies posted from the user's account use the account owner's first-person voice (`I`, `me`, `my`), including approval and landing notices. Do not refer to that account owner as `the user` or narrate an assistant intermediary. Ground actions, results, and approvals in actual work and authorization; separate bot reviews speak for the bot's identity. Keep titles concise and avoid drawn-out explanations. Cover related issues from commit messages, the problem and motivation, change type, tests, and risks.
  - **Issue Publication Reconciliation**: After publication, follow `skills/agent/github-fix-issues/references/integration.md` to confirm remote `main` contains the published commit and the PR has its expected head and native `MERGED` state before closure and cleanup. Persist publication state, first observation, deadline, and next poll across restarts. Use documented repository polling policy or the reference's 15-second/120-second fallback. Unresolved native state after the window suspends affected work without marking it complete or repeating publication to force a merged flag. Reuse current fetch/API results; do not add a separate connectivity check. Ordinary pending CI and running review remain governed by their existing gates.
  - **System (`system/`)**: Shared repo-level instruction fragments and memory guidance that can be referenced from harness configs or included into profile prompts belong here.
  - **Issue Queue Ownership and Restart**: Follow `skills/agent/github-fix-issues/references/queue.md` for verified single-writer ownership, task/worker identity, owned paths, and any scheduler-provided lease reference. Verify ownership before queue writes or resumed mutations; timestamps and lease expiry alone do not authorize takeover. Checkpoints do not dispatch workers. Use only an authorized, configured scheduler interface, record verified acceptance, or preserve state and report the exact redispatch requirement. Never invent leases or successful dispatch; reconcile live ownership, Git, issue/PR, CI, review, and publication state on restart.
  - **Self-Contained Logic**: Keep skills and commands self-contained; do not assume other skills are present. Matt Pocock's explicitly user-invoked workflows may depend on other bundled user skills; maintain their required dependencies. Keep all skills authored by `mattpocock` under `skills/user/`, as specified in `skills/AGENTS.md`.
- **The Harnesses (`harnesses/`)**:
  - Global configuration overrides for specific tools (e.g., `harnesses/opencode/opencode.jsonc`).
  - Unified harnesses can also provide repo-local build plugins at `packages/registry-cli/src/harnesses/<target>/build.ts`; `packages/registry-cli/src/commands/buildCommand.ts` statically imports those plugins.
  - When a task says to change OpenCode config "in ai-registry", edit the checked-in source file under `harnesses/opencode/`, not the machine-local installed config under `~/.config/opencode/`.
  - The checked-in OpenCode docs snapshot lives under `harnesses/opencode/docs/`; refresh it with `bun run sync:opencode-docs`, which runs `packages/registry-cli/src/bin/sync-opencode-docs.ts`.
  - Repository-local harness maintenance guidance belongs in `harnesses/AGENTS.md`.
  - Each harness contains a `fetch-source.sh` script to clone or update its upstream source code into a local, git-ignored scratch folder at `harnesses/<harness>/.tmp/<harness>-source/` for reference and inspection. These scripts and folders are omitted from the generated harness outputs using `.registry-ignore`.
  - **USE SOURCE REFERENCE FIRST:** When diagnosing harness-specific issues, analyzing behavioral contracts, or updating configurations, ALWAYS consult the local checked-out source code under `harnesses/<harness>/.tmp/<harness>-source/` first. Never guess, assume, or rely on memory. Run the respective `fetch-source.sh` first if the directory is absent.
  - Only files inside `harnesses/<target>/` are injected directly into the matching target output directories during the build process, subject to `.registry-ignore` rules.
  - Current generated harnesses are OpenCode (`harnesses/opencode/`), Codex (`harnesses/codex/`), Pi (`harnesses/pi/`), and Claude Code (`harnesses/claude-code/`).
- **Standalone Packages (`packages/<package-name>/`)**:
  - Publishable repo-local packages that are distributed independently from generated harness outputs live under `packages/`.
  - Add each standalone package to the root `package.json` workspaces so `bun install` manages it consistently.
  - Package-local guidance belongs in `packages/<package-name>/AGENTS.md` when a package has non-obvious contracts or validation rules. For the template resolver package, see `packages/template-resolver/AGENTS.md`.
- **Vendored Packages (`vendor/`)**:
  - Third-party code packages that need to live in this repo as Bun workspaces belong here.
  - Use this for repo-local harness dependencies such as file-based OpenCode plugins with runtime imports.
  - Vendored packages are repo-local runtime dependencies, not generated-output surfaces; reference them from source configs with `file://<%- repo_root %>/...` when needed, or symlink single files into generated roots from the harness build plugin.
  - Record the upstream repository, pinned commit, and file checksum in the vendored package's `README.md` so the copy stays reproducible.
- **The Profiles (`profiles/`)**:
  - Contains directories (e.g., `designer`, `developer`) with `profile.yaml` (or `profile.json`) manifests.
  - Manifests declare which skills and commands to include (supports globbing, e.g., `*`, `react-*`).
  - Profiles may also define top-level local assets at `profiles/<name>/commands/*.md` and `profiles/<name>/skills/<skill-name>/SKILL.md`.
  - Profile-local OpenCode commands are emitted as namespaced shared commands named `--<profile>-<filename>.md`.
  - Profile-local skills keep their normal names and must not collide with global skills or another profile's local skills.
  - Manifests can explicitly toggle native harness tools (e.g., `bash: false`) and inject custom tool-level permissions.
  - Manifests can define a custom `system_prompt` to give the agent specific baseline instructions.
- **External Skill Lock (`skills-lock.json`)**:
  - Records third-party skills vendored into `skills/` via the Skills CLI.
  - Commit it whenever you add or update external skills.

## Architecture & Build Process
This repository uses a custom build script (`packages/registry-cli/src/commands/buildCommand.ts` via `bun run build`) to locally compile the registry into ready-to-use configurations for harnesses directly from the checked-in source tree.
- **Unified Outputs:** The script generates final harness outputs in `.output/`. Today that includes `.output/opencode` for OpenCode, `.output/codex/<profile>` for Codex, `.output/pi/<profile>` for Pi, and `.output/claude-code/<profile>` for Claude Code. Generated harness skills across all harness outputs are merged flat from `skills/agent/`, `skills/user/`, `profiles/<profile>/skills/`, or `harnesses/<target>/skills/`, with build-time template tags resolved and `disable-model-invocation: true` automatically injected for user skills. Skills that are not authored by `alexgorbatchev` are emitted with their author prefix as `<author>-<skill>` in both directory name and frontmatter `name` across all harness outputs. They are copies rather than symbolic links so that EJS tags inside `SKILL.md` and bundled skill files reach the agent resolved; edits made to a generated skill are recovered through the generated-output drift and sync-back flow instead of writing straight through a link.
- **Harness Skill Override Precedence:** Harness-specific skills under `harnesses/<target>/skills/` (grouped into `agent/` and `user/`) take precedence over global skills (`skills/` and overlay `skills/`) on name collision across all four harnesses (OpenCode, Codex, Pi, and Claude Code). When a collision occurs, the harness-specific skill cleanly overrides the global skill in the generated output for that harness target.
- **Hostname Skill Variants:** Keep a default `SKILL.md` in each skill bundle. The build selects `variants/<hostname>/SKILL.md` within the resolved bundle using the OS hostname or `AI_REGISTRY_HOSTNAME`, with exact case-sensitive matching and default fallback when no matching directory exists. Hostnames start with a letter or digit and contain only letters, digits, dots, underscores, or hyphens; empty or invalid overrides fail. Matching variants must contain a regular `SKILL.md`, valid YAML frontmatter, a non-empty description and body, and the same name and author as the default. Selection follows existing overlay and harness precedence, applies to reusable, profile-local, and harness-local skills, and changes only the emitted root `SKILL.md`. Shared resources come from the bundle root; exclude its entire `variants/` directory from generated output. Keep actual private hostnames and environment instructions in the private overlay, which replaces whole bundles. Preserve the selected source mapping through template rendering and output assembly; `file_path` and `file_dir` refer to the selected variant's original path. The manifest records skill source paths, and sync-back rejects recovery when the recorded source differs from the current selection. Edit include-based skills at their source because sync-back does not reconstruct include directives.
- **Harness Plugins:** A harness can keep target-specific output shaping in `packages/registry-cli/src/harnesses/<target>/build.ts`. The root build runs a per-profile staging hook before final output assembly, then runs a finalize hook to produce the harness's final file layout.
- **No Top-Level Harness Code:** The top-level scripts (`packages/registry-cli/src/commands/buildCommand.ts` and `packages/registry-cli/src/commands/bootstrapCommand.ts`) MUST NOT contain any harness-specific generation logic, hardcoded template paths, or target-specific helper script generation. All such logic must live exclusively within the respective harness plugin (`packages/registry-cli/src/harnesses/<target>/build.ts`).
- **Generated Output Manifest:** Each successful unified build writes `.output/manifest.json` with managed files, directories, symlinks, mapped source paths, and source fingerprints. Treat harness-written changes in generated files as expected. During bootstrap, preserve session and runtime data and automatically recover supported generated-file edits into their mapped source when doing so will not overwrite source changes. Regenerate after successful recovery. If source and generated edits conflict, recovery is unsupported, or saving an edit fails, preserve both versions and suspend dependent output application with the exact conflict reported. Do not request confirmation merely because a harness changed a generated file. Recovery requires verified generated and source baselines and an exact reversal of supported transformations; includes, expressions, and control flow require source edits. Existing drift without source fingerprints must be reconciled into source before establishing a fresh baseline. Unmanaged harness-owned files are preserved. `-y` does not bypass recovery or conflict checks.
- **Harness Homes:** Harness runtime state (sessions, transcripts, history, databases, logs, installed plugins, credentials) never lives under `.output/`, so deleting `.output/` or moving the checkout cannot hide or split it. Each harness home is a real directory outside the repository: `${CLAUDE_CONFIG_DIR:-~/.claude}`, `${CODEX_HOME:-~/.codex}`, `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, and the OpenCode config directory for the default profile, and `${XDG_DATA_HOME:-~/.local/share}/ai-registry/<harness>/profiles/<profile>` for each non-default profile. Bootstrap symlinks into each home only the top-level entries `.output/manifest.json` records for that generated profile (managed entries plus `syncedFilePaths`); everything else in the home is harness-owned and left in place. Bootstrap repoints managed links that target another checkout, backs up a real entry occupying a managed name as `<name>.backup-<timestamp>`, removes dangling links into the generated profile or shared home, and refuses a home that is still a symlink. A non-default profile home also links every real entry of the default home it does not manage or already hold, except bootstrap's own `.backup-<timestamp>` copies, so profiles share runtime state. Harness plugins create no runtime directories in generated output.
- **Synced Settings Files:** Settings files a harness edits at runtime (Claude Code `default/settings.json`, Pi `default/settings.json`, OpenCode `opencode.jsonc`, Codex `default/config.toml`) are regular files in the generated output, never symlinks; harness homes reach them through bootstrap's managed links, and the manifest lists them under `syncedFilePaths`; the sync replaces a symlink left by an earlier layout with a copy of its target. They are registered through `buildSupport.syncSettingsFile(...)` in the harness plugin. They are excluded from `manifest.json` and never reported as drift. After the managed outputs sync, the build merges each key three ways: the live file, the newly rendered source, and the previous build's merged settings recorded under `.tmp/settings-sync/`. Harness-made additions, changes, and removals are written back to the registry source with repository paths reversed into template tags; source changes are applied to the live file; JSON, JSONC, and TOML are edited in place so comments and key order survive. When both sides changed the same value, lists combine both sides' edits, nested objects merge per key, and other values keep the source version with a printed warning. Without a recorded base, both sides are combined and the live value wins disagreements. Live-only key patterns (`*` matches any key) never reach the source: values a harness stamps on its own (Pi `lastChangelogVersion`, Codex `notice` and `tui.model_availability_nux`), entries keyed by or pointing at local paths (Codex `projects`, `skills.config`, `hooks.state`, and the `marketplaces.openai-bundled` entry Codex points at its own home), and fields that can hold credentials (OpenCode `mcp.*.headers` and `mcp.*.environment`, Codex `mcp_servers.*.env` and `mcp_servers.*.http_headers`). Source files that were tracked and clean before the sync are committed as `chore(settings): sync harness settings` with `git commit --only`, leaving other staged work alone; files that already had uncommitted edits keep the synced change uncommitted with a warning. Scheduled updates push those commits with the rest of the outgoing branch.
- **Source Tree Ignores:** When the build stages files from `skills/`, `commands/`, and `harnesses/<target>/`, it honors nested `.registry-ignore` files with `.gitignore`-style matching so repo-local scratch files can stay out of generated outputs.
- **Script Layout:** Executable repo entrypoints stay directly under `packages/registry-cli/src/bin/` and use dash-based filenames. TypeScript helpers that are imported by other scripts and are not meant to be run directly belong under `packages/registry-cli/src/lib/`.
- **Public CLI Helpers:** Any wrapper script intended for `~/.local/bin/` symlinking (for example `air-*`, `claude-*`, `codex-*`, or `pi-*`) MUST NOT be checked into `packages/registry-cli/src/bin/`. Instead, `packages/registry-cli/src/commands/buildCommand.ts` must generate them into `.output/bin/` during the build process, and `packages/registry-cli/src/commands/bootstrapCommand.ts` will symlink them from there.
- **Bootstrap Command:** `bun run bootstrap` is the repo-local setup entrypoint. It installs dependencies, builds the generated outputs, applies the generated OpenCode config to an XDG-style home unless `OPENCODE_CONFIG_DIR` is set, applies the generated Codex `default` profile to `${CODEX_HOME:-~/.codex}` unless `-- --codex-profile <profile>` overrides it, applies the generated Pi `default` profile to `${PI_CODING_AGENT_DIR:-~/.pi/agent}` unless `-- --pi-profile <profile>` overrides it, applies the generated Claude Code `default` profile to `${CLAUDE_CONFIG_DIR:-~/.claude}` unless `-- --claude-code-profile <profile>` overrides it, applies every non-default Codex, Pi, and Claude Code profile to its own profile home, and always refreshes the generated public wrappers in `~/.local/bin`. Applying a profile follows the Harness Homes rules.
- **Scheduled Updates:** `bun run scheduled:update` runs the repo-local `packages/registry-cli/src/bin/scheduled-update.ts` entrypoint. It creates `.tmp`, appends worker output to `.tmp/scheduled-update.log` with a local timestamp formatted as `[YYYY-MM-DD HH:MM]` on each line, and serializes manual and scheduled runs with macOS `lockf` or Linux `flock`, skipping overlaps. Each run prunes log entries older than 48 hours at minute precision and entries without the supported timestamp format. Its internal logger holds the native lock through pruning, worker execution, and all log writes. Its internal worker pulls the current branch's upstream with rebase and invokes bootstrap with `-y` on every run, so the build also syncs and commits settings the harnesses changed locally even when nothing arrives. It temporarily stashes tracked edits, restores staging state, and rolls back HEAD and edits if rebase or restoration fails. Untracked files stay in place and block incoming files that would overwrite them. Hooks are suppressed during the update and rollback to avoid duplicate bootstrap execution. `.tmp/scheduled-update-recovery.json` blocks retries after interruption or failed recovery; inspect its saved HEAD and stash and finish recovery before removing it. After a successful pull and bootstrap, it pushes outgoing commits only to the current branch's upstream without force or tags, including runs with no incoming changes. A failed bootstrap skips the push; push failures preserve commits for the next run to retry. Push hooks remain enabled, and GitHub pushes check outgoing messages and patches for restricted private domains.
- **Secret Scanning:** The checked-in `.githooks/pre-push` hook delegates to `packages/registry-cli/src/bin/scan-pushed-commits.ts`, which runs `gitleaks git` over every commit a push would publish (new history on updated branches, everything not on the remote for new branches) and blocks the push on findings. A missing or failing `gitleaks` blocks the push instead of passing it. The settings sync also scans each synced source file with `gitleaks dir` and leaves a change with findings uncommitted. Record reviewed false positives in `.gitleaksignore`. Schedulers invoke the entrypoint directly without wrapping it in another lock.
- **Codex Harness Mapping:** Bootstrap applies one generated ai-registry profile to `${CODEX_HOME:-~/.codex}`. The Codex harness copies the default profile's selected reusable and profile-local commands into every generated profile's `skills/` directory as native skill bundles, preserving command content as `SKILL.md` and setting `policy.allow_implicit_invocation: false` in `agents/openai.yaml`. Commands require YAML frontmatter with a non-empty `description`. An explicit frontmatter `name` determines the skill name; otherwise names use `command-<filename>` with leading hyphens removed and repeated hyphens collapsed (profile-local commands include the `default` namespace). Names must be lowercase kebab-case and at most 64 characters; duplicate command names and collisions with selected skills fail the build. Invoke these workflows with `$<skill-name>` or `/skills`. Codex outputs have no managed `prompts/` directory. Each profile renders its own `system_prompt` into home-level `AGENTS.md` and includes its own selected skills plus Codex-only shipped skills. The generated `default` root holds `config.toml` as a synced settings file rendered from `harnesses/codex/config.toml`; non-default roots symlink the remaining shared top-level entries from `.output/codex/default/`. Runtime files such as `auth.json` remain Codex-owned under the active `CODEX_HOME`. Non-default profiles inherit the default command set; their own command selections are not emitted. The output `bin/` directory contains `codex-<profile>` for non-default profiles only, each setting `CODEX_HOME` to that profile's home; no bare `codex` wrapper is generated.
- **Smoke Test:** `bun run bootstrap:smoke` validates the bootstrap flow against `.tmp/bootstrap-smoke/`, treating that directory as a fake `HOME` with the repo staged at `development/ai-registry`.
- **Pi Harness Mapping:** Pi has no native equivalent to OpenCode's `tools` and `permission` manifest fields. The Pi harness consumes `description`, `skills`, `commands`, and `system_prompt`, and it fails the build if a profile uses non-empty `tools` or `permission` values. The Pi harness treats generated `default` as the shared Pi base for reusable commands and shared settings: it maps the default profile's reusable commands to `prompts/`, renders each profile's own `system_prompt` content from `profiles/<name>/profile.yaml` into that profile's generated `APPEND_SYSTEM.md`, copies the shared `settings.json`, and copies any shipped `extensions/` under `harnesses/pi/extensions/`. Every non-default generated Pi profile root keeps its own `APPEND_SYSTEM.md` and `skills/` directory, includes any Pi-only shipped skills under `harnesses/pi/skills/`, and symlinks the remaining shared top-level entries from `.output/pi/default/`. The output `bin/` directory contains `pi-<profile>` for non-default generated Pi profiles only, plus the `pi-install`, `pi-update`, and `pi-uninstall` helpers; `pi-<profile>` sets `PI_CODING_AGENT_DIR` to that profile's home. No bare `pi` wrapper is generated, because the real `pi` binary already reads `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, where bootstrap applies the generated `default` profile.
- **Claude Code Harness Mapping:** Claude Code has no native equivalent to OpenCode's `tools` and `permission` manifest fields, so the Claude Code harness consumes `description`, `skills`, `commands`, and `system_prompt`, and it fails the build if a profile uses non-empty `tools` or `permission` values. The Claude Code harness treats generated `default` as the shared Claude Code base for reusable commands and shared settings: it maps the default profile's reusable commands to `commands/`, renders each profile's own `system_prompt` content from `profiles/<name>/profile.yaml` into that profile's generated `CLAUDE.md`, and copies every file shipped under `harnesses/claude-code/` except `skills/` into the default root. Every non-default generated Claude Code profile root keeps its own `CLAUDE.md` and `skills/` directory, includes any Claude Code-only shipped skills under `harnesses/claude-code/skills/`, and symlinks the remaining shared top-level entries from `.output/claude-code/default/`. The output `bin/` directory contains `claude-<profile>` for non-default generated Claude Code profiles only; `claude-<profile>` sets `CLAUDE_CONFIG_DIR` to that profile's home. No bare `claude` wrapper is generated, because the real `claude` binary already reads `~/.claude`, where bootstrap applies the generated `default` profile. It also generates the `cll` helper for launching Claude Code through an on-prem or remote LiteLLM proxy.
- **Generated Output Templates:** Keep source filenames and use native EJS syntax in text files. Use raw output tags such as `<%- repo_root %>`, `<%- file_path %>`, and `<%- file_dir %>`; the latter two identify the original source across nested includes. Use `<%- include("/system/system.md") %>` for repository-root-relative includes and `<%- env("VAR_NAME", "fallback") %>` for environment values with an optional fallback. EJS expressions and control flow are supported. Render each file exactly once; `<%%` emits a literal opening delimiter. Foreign `{{...}}` syntax passes through unchanged. Unknown variables, invalid JavaScript, missing includes, and missing environment values without fallbacks fail the build. Resolved includes cannot escape the repository root. Templates execute trusted JavaScript. Generated-edit recovery supports canonical raw path-variable tags; edit other EJS templates at their source.
- **Canonical Path References:** When checked-in guidance or generated text needs a canonical path inside this repository that would otherwise be machine-specific and absolute, use template variables instead of hardcoded absolute paths. Prefer the most specific token available for canonical folders: `<%- skills_dir %>/...`, `<%- commands_dir %>/...`, `<%- profiles_dir %>/...`, and `<%- output_dir %>/...`. For canonical folders without a dedicated token, anchor the path from `<%- repo_root %>`, such as `<%- repo_root %>/harnesses/...`, `<%- repo_root %>/system/...`, `<%- repo_root %>/vendor/...`, `<%- repo_root %>/packages/registry-cli/...`, `<%- repo_root %>/README.md`, and `<%- repo_root %>/AGENTS.md`. Use normal repo-relative paths elsewhere in checked-in docs.
- **Private Overlay Registries (`AI_REGISTRY_OVERLAY`):** To support proprietary or work-specific skills, commands, and profiles that cannot be committed to this public repository, the build supports an external overlay directory via the `AI_REGISTRY_OVERLAY` environment variable (autoloaded from `.env` via Bun). When set, `bun run build` merges skills from `<overlay>/skills/`, commands from `<overlay>/commands/`, and profiles from `<overlay>/profiles/` with the public registry. Overlay assets override base assets on name collision. Generated templates can also reference `<%- overlay_dir %>`.

## Development Workflow
- Automatically record explicit standing user instructions, such as “always do X” or “never do Y,” in the narrowest applicable `AGENTS.md` or existing policy file without requiring a separate request to save them. Update an existing rule in place when the user clearly changes it. Keep one-task directions, progress, handoffs, and session data out of policy files. Ask only when the intended policy scope or resolution of a material conflict is unclear.
- Let models choose search and code-navigation tools according to the task and available capabilities; do not add mandatory tool ordering or tool-specific stop rules.
- Keep dependency investigation and library integration within the authorized task's required capabilities. Follow the shared library guidance in `system/system.md`.
- Apply the shared red/green and test-sensitivity rules to changes in executable behavior; use applicable validators for non-executable changes. Keep sensitivity checks isolated from other actors' changes, following `system/system.md`.
