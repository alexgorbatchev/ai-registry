# Instruction audit for unattended software work

The highest-priority changes are to replace whole-run halts with task-specific suspension, recognize standing authorization, remove mandatory interactive checkpoints from execution workflows, and define bounded recovery with durable resumption. Removing every approval or quality gate would undermine the ownership, publication, and verification protections the factory needs.

This report is for maintainers designing unattended workers. It identifies source instructions that can interrupt work, consume an unbounded run, or conflict with other instructions. Recommendations describe proposed policy changes; they are not active instructions. This audit does not modify the operating rules or authorize publication, integration, deployment, or deletion.

## Scope and evidence

Unattended execution is a requirement for reusable workflows intended for unattended workers, not a default requirement for maintaining this registry. The registry is maintained interactively with agent assistance. Local rules are not defects merely because they involve a human decision; assess redundant authorization requests and unclear policy-recording behavior separately.

Commands are explicitly invoked manual workflows and are excluded from this review at the user's request. This exclusion covers reusable, profile-local, and harness-local commands, including command bundles emitted as native skills. Command-only findings A27/A36/A37 and the command portions of A29/A35 and the contradiction table are withdrawn from the remediation queue. Q34 is withdrawn without applying its proposal. Earlier authorized command fixes remain; this scope change does not revert them. See I033 in the issue inventory.

## Broad reach of the shared rules

Every generated harness ships every registry skill and command together with [system/system.md](../../../system/system.md) as its system prompt. Changing only one worker's task prompt will leave the shared stopping rules in place.

Selected skills are available rather than all simultaneously active. [AGENTS.md](../../../AGENTS.md) documents build-time disabling of implicit invocation for user skills, and the triage/to-tickets `agents/openai.yaml` files explicitly disable implicit invocation. Their mere presence does not prove they interrupt a run. Explicitly invoked manual workflows do not require unattended replacements merely because a profile includes them. Commands remain outside this review.

The legacy [Claude installation guide](../../../INSTALL_CLAUDE_SKILLS.md) also documents installing the shared system prompt directly. Policy changes need a rollout path for consumers of both bootstrap and that installer.

## Original factory-contract proposal

This initial proposal is historical. Subsequent decisions retain one active issue while ordinary CI/review is pending and the existing design/ticket review-until-clean loops. Necessary prerequisite repairs are bounded; compatibility requires explicit authorization. Runtime scheduling remains an implementation gap. Do not treat this proposal as an approved change to those policies.

The current sources contain useful pieces: persistent queue reconstruction, bounded polling, exact revision checks, explicit retry for scheduled bootstrap, independent review, and instructions to honor existing authorization. They do not combine those pieces into a consistent unattended execution contract.

The proposed contract needs these explicit decisions:

1. **Task envelope.** Record repository, target/base revision, acceptance criteria, owned worktree, permitted dependencies/network/secret references, and separate grants for commit, push, issue/PR creation, integration, release, deployment, and deletion. Record time/cost/retry/concurrency limits. A broad “be autonomous” sentence cannot resolve all these scopes safely.
2. **Delegated implementation decisions.** Permit reversible choices supported by the approved requirements and existing architecture. Record significant choices and their evidence. Essential missing product decisions remain unresolved; ordinary implementation detail does not require a human vote.
3. **Recovery order.** Inspect the failure, retry only appropriate transient failures, repair allowed local prerequisites, use a verified permitted alternative, then suspend the dependent task/action. Do not retry authentication or policy denials endlessly, change identities opportunistically, or weaken required checks.
4. **Durable task states.** Distinguish runnable, running, waiting for CI/review/dependency, awaiting authorization/product input, integration-ready, completed, and failed. A suspended task records the exact reason, last verified state, attempts, retained artifacts, next action, and resume event/time. None of these states means completion unless acceptance and integration requirements are satisfied.
5. **Independent progress.** Let the scheduler select another authorized eligible item when the current item is suspended and resources can be isolated. Preserve dependency edges and one owner per task. A serialized integration lane can coexist with independent implementation work; this requires revising the current one-issue-through-cleanup policy.
6. **Ownership and checkpoints.** Assign worker/task leases and isolated worktrees. Never seize an index, delete a lock, adopt another worker's staged work, or overwrite shared runtime output. On restart, reconcile checkpoint state with actual Git and remote issue/PR/CI state before acting.
7. **Bounded review and waiting.** Configure budgets and backoff instead of adding arbitrary universal numbers to prompts. Exhausted budgets suspend with actionable state. Required CI, independent review, or acceptance defects remain gates; optional improvement does not create an endless rewrite loop.
8. **Exception handling.** Route only genuinely nondelegated decisions to a human queue. Prepare the complete reviewable candidate before requesting approval. While approval is pending, continue independent authorized work. Authorization never arrives merely because a timeout elapsed.
9. **Completion evidence.** Report actual results, revision, required check status, approval/integration state where applicable, and remaining blockers. Do not fabricate success, treat absent CI as green, or describe a staged transfer or unmerged PR as finished delivery.

An instruction file can require checkpointing and explain how to resume. A scheduler/worker runtime still needs to implement wakeups, leases, retries, and restart dispatch. The repository's documented scheduled updater refreshes registry configuration; it is not evidence of a software-task scheduler.
