# Registry state and bootstrap contracts

For agents modifying or diagnosing these contracts. Paths are relative to the repository root.

## Generated Output Manifest

Each successful unified build writes `.output/manifest.json` with managed files, directories, symlinks, mapped source paths, and source fingerprints. Treat harness-written changes in generated files as expected. During bootstrap, preserve session and runtime data and automatically recover supported generated-file edits into their mapped source when doing so will not overwrite source changes. Regenerate after successful recovery. If source and generated edits conflict, recovery is unsupported, or saving an edit fails, preserve both versions and suspend dependent output application with the exact conflict reported. Do not request confirmation merely because a harness changed a generated file. Recovery requires verified generated and source baselines and an exact reversal of supported transformations; includes, expressions, and control flow require source edits. Existing drift without source fingerprints must be reconciled into source before establishing a fresh baseline. Unmanaged harness-owned files are preserved. `-y` does not bypass recovery or conflict checks.

## Harness Homes

Harness runtime state (sessions, transcripts, history, databases, logs, installed plugins, credentials) never lives under `.output/`, so deleting `.output/` or moving the checkout cannot hide or split it. Each harness home is a real directory outside the repository: `${CLAUDE_CONFIG_DIR:-~/.claude}`, `${CODEX_HOME:-~/.codex}`, `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, and the OpenCode config directory. Bootstrap symlinks into each home only the top-level entries `.output/manifest.json` records for that harness output (managed entries plus `syncedFilePaths`); everything else in the home is harness-owned and left in place. Bootstrap repoints managed links that target another checkout, backs up a real entry occupying a managed name as `<name>.backup-<timestamp>`, removes dangling links into the harness output, and refuses a home that is still a symlink. Harness plugins create no runtime directories in generated output.

## Synced Settings Files

Settings files a harness or a third-party installer edits at runtime (Claude Code `settings.json` and `keybindings.json`, Pi `settings.json`, OpenCode `opencode.jsonc` and `tui.json`, Codex `config.toml` and `hooks.json`) are regular files in the generated output, never symlinks; harness homes reach them through bootstrap's managed links, and the manifest lists them under `syncedFilePaths`; the sync replaces a symlink left by an earlier layout with a copy of its target. They are registered through `buildSupport.syncSettingsFile(...)` in the harness plugin. A synced file registered with `shouldLinkIntoHome: false` is rendered into the generated output but never linked into a harness home; Claude Code's `claude.json` uses it. They are excluded from `manifest.json` and never reported as drift. After the managed outputs sync, the build merges each key three ways: the live file, the newly rendered source, and the previous build's merged settings recorded under `.state/settings-sync/`. Harness-made additions, changes, and removals are written back to the registry source with repository paths reversed into template tags; source changes are applied to the live file; JSON, JSONC, and TOML are edited in place so comments and key order survive. When both sides changed the same value, lists combine both sides' edits, nested objects merge per key, and other values keep the source version with a printed warning. Without a recorded base, both sides are combined and the live value wins disagreements. Live-only key patterns (`*` matches any key) never reach the source: values a harness stamps on its own (Pi `lastChangelogVersion` and `extensionChangelogVersions`, Codex `notice` and `tui.model_availability_nux`), entries keyed by or pointing at local paths (each Codex `projects` entry, `skills.config`, and `hooks.state`; Codex and ChatGPT desktop app entries that point at machine-local binaries and caches: `notify`, `marketplaces.openai-bundled`, `marketplaces.openai-primary-runtime`, `mcp_servers.node_repl` (except registry entries in `env.NODE_REPL_TRUSTED_SERVICES`, merged into its JSON object after live-only preservation while retaining app-added services, and only while the app-written server declares a `command` or `url` transport; otherwise the registry entries are removed and no `node_repl` server is created, because Codex refuses to start on a server without a transport), and `mcp_servers.cua_repl`), and fields that can hold credentials (OpenCode `mcp.*.headers` and `mcp.*.environment`, Codex `mcp_servers.*.env` and `mcp_servers.*.http_headers`). Source files that were tracked and clean before the sync are committed as `chore(settings): sync harness settings` with `git commit --only`, leaving other staged work alone; files that already had uncommitted edits keep the synced change uncommitted with a warning. Scheduled updates disable settings auto-commit with `AI_REGISTRY_SETTINGS_AUTO_COMMIT=0` and leave synced edits uncommitted; they push only existing outgoing commits.

## Local Storage

`.tmp/` holds only disposable development artifacts: test fixtures, build staging and scratch, coverage, the bootstrap smoke home, and harness source fetches under `harnesses/<harness>/.tmp/`. Anything that must survive a session goes in git-ignored `.state/` (settings-sync merge bases, the entries bootstrap applied to harness-owned settings files, and the scheduled update's log, lock, and recovery marker) or `.cache/` (rebuildable caches). Never move or clear `.state/` as cleanup.

## Bootstrap Command

`just bootstrap` is the repo-local setup entrypoint. It refuses to run at the top level of a linked Git worktree, before installing or building anything, and names the primary checkout: harness homes are machine-wide and link into the bootstrapped checkout's output, which a worktree takes with it when removed. Use `just build` to verify a worktree. No Git hook runs bootstrap; `.githooks/` holds only `pre-push`. `just build` changes nothing outside the registry checkout and its overlays; writing harness configuration on the machine belongs to bootstrap. Claude Code reads user-scope MCP servers only from its global `.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` or `~/.claude.json`), so the build renders `harnesses/claude-code/claude.json` with overlays merged into `.output/claude-code/claude.json`, and bootstrap writes its `mcpServers` entries into the global file, leaving every other key and servers added in Claude Code alone. `.state/bootstrap/claude-code/claude.json.json` records the entries bootstrap applied, so it removes entries the registry stops declaring; entries changed outside the registry since the last bootstrap are replaced, or kept once no longer declared, with a warning; `headers` and `env` stay as Claude Code stored them. It runs `just setup` to install dependencies and point Git at `.githooks`, builds the generated outputs, applies the generated OpenCode config to an XDG-style home unless `OPENCODE_CONFIG_DIR` is set, applies `.output/codex` to `${CODEX_HOME:-~/.codex}`, `.output/pi` to `${PI_CODING_AGENT_DIR:-~/.pi/agent}`, and `.output/claude-code` to `${CLAUDE_CONFIG_DIR:-~/.claude}`, and always refreshes the generated public wrappers in `~/.local/bin`, removing broken links to wrappers the build no longer generates. Applying an output follows the Harness Homes rules.

## Scheduled Updates

`just scheduled-update` runs the repo-local `packages/registry-cli/src/bin/scheduled-update.ts` entrypoint. It creates `.state`, appends worker output to `.state/scheduled-update.log` with a local timestamp formatted as `[YYYY-MM-DD HH:MM]` on each line, and serializes manual and scheduled runs with macOS `lockf` or Linux `flock` on `.state/scheduled-update.lock`, skipping overlaps. The workspace scheduler takes the same lock for this checkout, so keep that path stable. Each run prunes log entries older than 48 hours at minute precision and entries without the supported timestamp format. Its internal logger holds the native lock through pruning, worker execution, and all log writes. Its internal worker pulls the current branch's upstream with rebase and invokes bootstrap with `-y` on every run, so the build also syncs settings the harnesses changed locally without creating commits, even when nothing arrives. A checkout with staged, unstaged, or untracked changes skips the pull and push and still bootstraps, so harness settings keep syncing; never stash or rewrite uncommitted work, because restoring it can conflict and rewriting its files resets the commit sweep's quiet window. A failed rebase rolls back HEAD. Hooks are suppressed during the update and rollback. `.state/scheduled-update-recovery.json` blocks retries after interruption or failed recovery; inspect its saved HEAD and finish recovery before removing it. After a successful pull and bootstrap, it pushes outgoing commits only to the current branch's upstream without force or tags, including runs with no incoming changes. A failed bootstrap skips the push; push failures preserve commits for the next run to retry. Push hooks remain enabled, and GitHub pushes check outgoing messages and patches for restricted private domains.

## Secret Scanning

The checked-in `.githooks/pre-push` hook delegates to `packages/registry-cli/src/bin/scan-pushed-commits.ts`, which runs `gitleaks git` over every commit a push would publish (new history on updated branches, everything not on the remote for new branches) and blocks the push on findings. A missing or failing `gitleaks` blocks the push instead of passing it. When settings auto-commit is enabled, the settings sync scans each clean synced source file with `gitleaks dir` and leaves a change with findings uncommitted. Record reviewed false positives in `.gitleaksignore`. Schedulers invoke the entrypoint directly without wrapping it in another lock.

## Smoke Test

`just bootstrap-smoke` validates the bootstrap flow against `.tmp/bootstrap-smoke/`, treating that directory as a fake `HOME` with the repo staged at `development/ai-registry`.
