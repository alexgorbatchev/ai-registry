# Lessons and pitfalls

Each lesson names the situation where agents go wrong, what it cost, and the rule this skill now requires. Where a linked reference holds the full rule, follow that reference; the lesson only says why it exists. Examples marked illustrative use an invented reporting app.

## Delivery and durability

- **L1 Deliver per unit, not at the end.** Trigger: review or design agents run for hours over a whole area, keep results in memory, and write files, file tickets or publish only after every phase finishes. Consequence: routine interruptions erased hours each time: a provider outage, a session time limit, a host reboot, and, in one harness, a stalled model request that its watchdog aborted before the workflow engine restarted the agent from zero. One effort reached 9 hours with zero tickets, and only 4 of 16 review areas left a findings file. Rule: units of about 30 minutes, split by flow, area slice or ticket; each checkpoints after every result, validates its handoff file where one applies, and is delivered within the authorized scope as soon as it is verified, with no global barrier before anything ships; relaunches skip units whose last stage is done. This holds in every phase, including pattern-reference audits, authoring and critique: a design run launched without checkpoints died with the session and restarted from nothing. Mechanics: [orchestration](orchestration.md); who commits: [SKILL.md](../SKILL.md) "Scope boundaries".
- **L2 Run services and keep scripts outside the session.** Trigger: the app, its API and the docs server run as session background jobs, and launcher scripts live in session temp. Consequence: a 2-hour background-job limit killed the dev stack mid-review; a reboot killed every reviewer, 22 isolated app instances and their browsers, and wiped the session temp directory along with the launcher script. Rule: start services detached or supervised with an idempotent command, health-check them before launching agents and during use, keep agents from starting or stopping shared services, and keep scripts, checkpoints and partial outputs under `<state>`. A terminal multiplexer survives a session limit but not a reboot; only resumable units survive a reboot. Details: [orchestration](orchestration.md) "Services".
- **L3 Diagnose a death from its own record.** Trigger: agents keep dying and the lead names a cause from timing, such as deaths coinciding with its own wake-ups. Consequence: a wrong diagnosis and a "fix" that prevented nothing; the records showed all 15 deaths came 583–600 seconds after a model request that never answered, which that harness's watchdog aborted and logged as a user interrupt. Rule: read each dead agent's or process's termination record (exit status, log tail, final transcript entries) before naming a cause; report timing correlation as a hypothesis; retract a wrong diagnosis explicitly. What an "interrupted" marker means differs between harnesses: check the harness's documentation or logs before reading one as a user action. Details: [orchestration](orchestration.md) "Failures".
- **L4 Salvage dead units before rerunning them.** Trigger: many units die after hours of browser exploration. Consequence: rerunning repeats hours of work under the same interruptions; salvage finished 11 dead areas in 27 minutes with no restarts and produced 142 findings. Rule: digest each dead unit's transcript, screenshots and annotation labels, run short browser-free units over the digests, and re-queue a unit whose digest holds nothing usable as a first-class unit of the next run. Procedure: [review](review.md) "Salvage".
- **L5 Re-check the claim before every commit, push, release or ticket change.** Trigger: claimed tracker work goes to a background worker that checks the claim once at start, while the lead's thread looks idle because background workers do not show there. Consequence: another session read the idle thread as abandoned, released the claim and built the same ticket; the worker committed after losing its claim, wasting about 40 minutes of agent work and leaving two implementations to compare. Rule: before every commit, push, release or ticket change, whoever makes it (the orchestrator, a unit filing its tickets, Phase 8's delivery stage) re-checks that the run still holds the task's claim, and stops and saves the work when it is gone; a background run that holds a claim gets a ticket comment naming the run, where its journal and checkpoints live, and how to tell it is alive. Details: [orchestration](orchestration.md#ownership) "Ownership".

## Coverage

- **L6 Give every feature one owning flow.** Trigger: flows are enumerated by tool page or surface, and the owner's word for a feature differs from the app's label. Consequence: a capability reachable from three flows had a piece in each and no flow owned its journey (illustrative: "Replace data source…" offered from the report editor, the export validator and the import tool); it was the riskiest flow, and the owner had to ask whether it had been missed or was named something else. Rule: apply the Phase 1 mapping, risk ranking and gate in [SKILL.md](../SKILL.md); find the owner's term by searching source and UI labels for it and its synonyms, and record the mapping in `flows.md`.
- **L7 Run gap rounds for cross-cutting concerns.** Trigger: the review partitions by surface and stops after the first wave. Consequence: a later completeness pass found 48 new findings in five areas the partition missed: interruption recovery (including a P0 where a lost response replayed a write and created two undo records), rule editors, large-data scale, accessibility semantics of bulk dialogs, and history-derived views. Rule: run the completeness pass after the first wave, expecting failure and offline states, scale, accessibility and rule editors to be under-covered. Procedure: [review](review.md) "Completeness".
- **L8 Start a late-found flow with research, not visuals.** Trigger: a missing flow turns up after other flows already have diagrams and wireframes. Consequence: visuals drawn at once would start out inconsistent with the pattern reference still being written. Rule: give it a code-research note (`proposals/<key>-research.md`) and a written proposal first; draw its diagrams and wireframe after the reference exists (unless the owner chose provisional mode for it), then conform them like every other flow.

## Rework instead of patching

- **L9 Absorb findings into the redesign.** Trigger: review tickets stay open with their own priorities while redesigns are planned. Consequence: 169 of 219 finding tickets fell under a redesign; an agent working the queue by priority would have spent weeks patching screens the rework deletes. Rule: one redesign ticket per flow absorbs that flow's findings as acceptance evidence and carries their priority; foundation redesigns (selection, progress and jobs, undo) come before the flows that depend on them. Blocking and re-prioritizing tickets, and when that needs the owner's approval, follow [proposals and tickets](proposals-and-tickets.md#filing) "Filing".
- **L10 Allow stopgaps only for live data loss.** Trigger: P0 findings tempt standalone fixes ahead of the redesign. Consequence: patch work the rework throws away, or a stopgap that contradicts the redesign. Rule: only bugs that damage data now get a standalone stopgap, matching what the redesign specifies ([proposals and tickets](proposals-and-tickets.md) "Stopgaps"). Apply L23 before calling anything data loss: one proposed stopgap would have blocked the exact behavior the owner wanted.

## Shared reference and consistency

- **L11 Write the shared reference before parallel design.** Trigger: flow proposals are split across parallel agents, each working from its own flow's tickets. Consequence: the proposals diverged on selection, menus, footers, surfaces, review, feedback, undo, keyboard and wording; the later audit counted 159 cross-cutting decisions, about 120 of them in conflict. A "shared patterns" list assembled afterwards from noticed overlaps bound nobody. Rule: Phase 5 finishes before Phase 6 starts and every design agent receives the reference; flows already designed without one, or drawn in provisional mode ([SKILL.md](../SKILL.md) step 2), stay untouched while it is written and are conformed in Phase 8; a cross-flow check runs before delivery, and conflicts block it. Interruption resilience does not provide consistency; both are needed. Details: [pattern reference](pattern-reference.md) "When".
- **L12 Check the exemplar against the reference before fan-out.** Trigger: parallel wireframe agents get one example page that was drawn without checking it against the reference. Consequence: the exemplar drew a selection bar inside the table that another flow's proposal explicitly removed; most pages copied it, so the one shared artifact spread a contradiction instead of catching one. Rule: draw one exemplar, check it rule by rule against the reference, fix it, and only then hand it to parallel designers.
- **L13 Measure an inconsistency across all pages before answering.** Trigger: the owner asks whether pages disagree, for example about where selection actions live. Consequence: answering from memory or fixing the cited page leaves the rest diverging; the measured spread was one flow moving the selection summary and a single Actions menu into the shortcut bar, three flows keeping action buttons in an in-table bar, two keeping an older menu name, and one drawing both bars. Rule: count each variant's markers on every page with a text search, report the measured spread, add a conflicts-list entry with a recommendation, and settle it in the reference rather than in one page ([design language](design-language.md) "Bars").
- **L14 Classify a wireframe problem before fixing it.** Trigger: the owner flags something wrong on a wireframe. Consequence: silently redrawing a faithful drawing of a flawed proposal makes the wireframe disagree with its proposal and ticket. Rule: fix a drawing error; keep a faithful drawing of a proposal error, mark it as an open conflict and settle it through the reference before Phase 8 redraws it; after one instance of either, audit every page for the same mistake. Procedure: [design language](design-language.md) "Drawing errors and proposal errors".
- **L15 Keep mockups and rule text in sync.** Trigger: a rule's text or its mockup is edited alone. Consequence: the visual reference's menu mockup omitted an item the written rule listed, unnoticed until another fix touched that menu. Rule: review each mockup against its rule's text in the same pass and change both in one edit; a mismatch either way is a defect ([design language](design-language.md) "The pattern page").

## Wireframe design language

- **L16 Give every convention a legend meaning.** Trigger: a visual convention, such as a dark inverse-colour box, is used without saying what it means. Consequence: the owner asked whether the inverse colour meant something or was a mistake; it meant "toast", but no page said so, and one proposal had put Cancel and Apply inside a toast and listed per-item failure reasons there. Rule: every page with mockups carries the "How to read" legend, with an entry for every convention they use; a toast is a transient status sentence with links only, never a decision, a choice or a list someone must keep, because it disappears on its own and screen readers announce it once without letting anyone move into it. Decisions go in a panel, popover or dialog. Rules and linter checks: [design language](design-language.md) "Legend" and "Vocabulary".
- **L17 Anchor every popover to its trigger.** Trigger: a popover or menu is drawn wherever it fits in the mockup. Consequence: a destination picker floated in a corner connected to nothing; an audit found two more menus drawn at the top of the window with their triggers at the bottom; the first re-anchoring guessed an offset and still covered the trigger. Rule: point the caret at the outlined trigger, name the opener, and measure offsets in a browser, confirming them with cropped screenshots ([design language](design-language.md) "Vocabulary").
- **L18 Make each step stand alone and say what stays.** Trigger: a step adds an entry point, and only a later step explains how it relates to the existing ones. Consequence: the owner screenshotted the step alone and read a new footer Actions button as replacing right-click. Rule: each step's caption is complete on its own and says what stays as well as what changes ([design language](design-language.md) "Steps and callouts").
- **L19 Put menu headings over two or more items.** Trigger: menu items are grouped mechanically, one heading per category. Consequence: a heading over a single item ("History" over "History…") read as broken to the owner. Rule: a heading labels two or more items, a lone item joins its closest related group, and only the destructive last item stands alone after a separator ([design language](design-language.md) "Menus").
- **L20 Keep the legend sticky with CSS only.** Trigger: the legend sits in the page header, or a script is added to pin it. Consequence: the key scrolled away while the owner read the mockups, and the owner asked for current browser CSS with no JavaScript. Rule: use the CSS-only sticky key band right after the header, and re-measure `--key-h` in a browser at several widths after any font or legend change, because monospace text is wider. Details: [design language](design-language.md) "The sticky key" and "Tokens".
- **L21 Link one stylesheet with one font token.** Trigger: a versioned shared CSS block is copied into every page, or pages set their own fonts. Consequence: every style change became a bulk rewrite of every page plus hash checks that the copies still matched, page-local menu CSS drifted between pages, and the owner asked for one linked stylesheet instead. Rule: every page, the index included, links `wireframe.css`, keeps only page-specific rules in its own `<style>`, never redefines shared tokens, and sets every font through `var(--font)`. Details and linter checks: [design language](design-language.md) "Files" and "Tokens".
- **L22 Use the full window width.** Trigger: `main` gets a `max-width` cap for readability. Consequence: wide screens showed a huge empty gap beside the pages, which the owner rejected ("don't cap the layout"). Rule: no cap on `main`; mockups and captions grow with the window, and only text blocks keep a reading cap ([design language](design-language.md) "Layout").

## Product intent and evidence

- **L23 Check stated intent before calling behavior a defect.** Trigger: a research agent reads code, finds behavior that looks harmful, and the lead repeats its verdict (illustrative: an import that replaces a report with a longer revision whenever it scores higher). Consequence: intended product behavior was framed as a P0 data bug, with a stopgap that would have blocked the exact action the owner wanted; the owner noted it was not the first time. The owning component's docs stated the intent; the repository where the design agents worked did not. Rule: read the owning component's docs and tests for its stated intent before calling behavior a defect; answer feature-semantics questions with a decision table citing code; when the implemented rule conflicts with the owner's stated rule, ask an ID'd question with a recommendation. Record each owner rule in the project instructions where design agents work and in every agent's shared context; a recurring misunderstanding is a documentation gap to fix. Procedure: [pattern reference](pattern-reference.md) "Fact-checking a high-severity claim".
- **L24 Turn hazards of intended behavior into warnings, then purge the old framing.** Trigger: intended behavior carries a real hazard, or an artifact has just been reframed. Consequence: a gate that blocks the action defeats the feature; reframed artifacts that keep words like "P0", "defect" or the withdrawn gate's name keep misleading later agents. Rule: warn at the point of choice and again in the result, with the concrete effect and explicit choices; ship the cheap, detectable slice first; after any reframing, search every artifact for the superseded wording and remove it.
- **L25 Check the instrument before confirming runtime behavior.** Trigger: the owner asks whether something works, the answer depends on a measurement (a detector, scorer or classifier), and the agent confirms by reading code. Consequence: the agent said yes; a later measurement showed the detector returned the same value for every input, so the confirmed path never triggered, and the answer had to be retracted. Rule: a reading of code is a claim about code, not about what users get; before confirming runtime behavior, run the instrument on known inputs (the ladder in L26) and say which kind of claim you are making; when evidence changes, correct the earlier answer explicitly, by its ID.
- **L26 Measure defaults on a calibration ladder.** Trigger: the owner delegates a threshold or default, and the agent picks a plausible value. Consequence: the first recommendation, chosen without measuring, sat just below the score of a common low-quality tier, so it would have passed the very inputs the default existed to reject. Rule: choose the value from a measured ladder of representative real inputs and record the table with the decision; a broken instrument blocks the default and is filed. Procedure: [pattern reference](pattern-reference.md) "Product decisions".

## Owner review

- **L27 Ask for decisions as a short ID'd table.** Trigger: reference output goes to the owner as long prose or a full rule list. Consequence: the owner has to dig for what changes; given a table, the owner answered eight such items in one line each ("i2 yes", "i3 clarify"). Rule: list only decisions that change how the product feels day to day, one row each (ID, today, proposed, rule IDs); state back your reading of a terse or ambiguous answer so the owner can correct it. Format: [pattern reference](pattern-reference.md) "Owner review".
- **L28 Record every verdict and carry reversals everywhere.** Trigger: the owner reverses a proposed rule, and the agent updates the decision log only. Consequence: the contract-change list, per-flow conformance, proposals, wireframe hints, index cards and the visual page's tables would still state the reversed rule. Rule: record each verdict by rule ID, carry each reversal to every artifact that stated it, search all artifacts for leftovers, and bump the revision ([pattern reference](pattern-reference.md) "Owner review").
- **L29 Return unclear items as scenarios.** Trigger: the owner answers "clarify". Consequence: about a third of the flows depended on one unclear item, and conforming flows to a decision that may still change wastes the work. Rule: answer with a concrete scenario that sets today against the proposal, with the cost and the flows that depend on it; reconciliation starts only when every reviewed decision is settled, and work that does not depend on the answer continues meanwhile ([pattern reference](pattern-reference.md) "Owner review").
- **L30 Re-list open questions with their context.** Trigger: a question ID comes back hours later ("q4 ?"). Consequence: the owner cannot answer without scrolling back through the conversation. Rule: re-read the state, then restate the background, what changed since the question was asked, and the options as nested IDs (`q4a1`, `q4a2`) with a recommendation; never reuse an ID for a new item.

## Publishing and reporting

- **L31 Move design artifacts out of scratch early.** Trigger: proposals, wireframes and research notes stay in a scratch directory. Consequence: a scheduled cleaner deletes scratch entries unchanged for 24 hours, and two dozen proposals plus a research note sat there until the owner asked for them in the repository. Rule: move design artifacts into the docs tree as soon as anyone else needs to see them, keep working files under `<state>/ux-flows/`, and delete scratch copies of the owner's private data ([publishing](publishing.md) "Where artifacts live").
- **L32 Run the docs-site tests after adding a new kind of page.** Trigger: wireframes, Markdown pages or new folders join a docs site whose tests and build recipe assume one kind of page. Consequence: two docs-site test suites failed for several commits: one expected every page to be a diagram, and a build loop failed on a glob that matched no files. Rule: after adding any new kind of page, run and extend the docs-site tests, guard globs against matching nothing, and confirm each test fix fails without it ([publishing](publishing.md) "Docs-site tests").
- **L33 Link pages, not folders, and crawl before reporting.** Trigger: a page links a directory. Consequence: the docs server did not map the folder to an index page, so the link was broken, and only a crawl of the live site found it. Rule: link the index page itself (`wireframes/index.html`), and crawl the served site and fix every reported problem before reporting ([publishing](publishing.md) "Link crawl").
- **L34 Serve every file type the pages link.** Trigger: pages switch to a linked stylesheet on a docs server that serves only HTML and Markdown. Consequence: the stylesheet does not arrive as `text/css`, the browser ignores it, and every wireframe renders unstyled. Rule: after publishing, request the stylesheet URL and confirm a 200 response with `text/css`. Server requirements: [publishing](publishing.md) "Serving".
- **L35 Report visual coverage honestly, with a way in.** Trigger: pages pass status checks, lint and the crawl, and the report says "verified". Consequence: "every URL returns 200" reads as "every page was reviewed"; in one delivery 46 diagrams returned 200 and only one pair had been inspected, which the report had to say. A delivery message without a preview path left the owner asking how to open the pages. Rule: say which pages had visual inspection and which passed automated checks only, and give every delivery message clickable preview URLs, the file layout, an offline way in and the server restart command ([publishing](publishing.md) "Visual evidence" and "Reporting").
- **L36 Use the project's tools and rules.** Trigger: an agent formats files or writes commits the way its tools usually do. Consequence: artifacts were formatted with a generic formatter instead of the project's own, and a commit message was written with a heredoc despite a project rule against heredocs. Rule: format proposals, `patterns.md`, wireframes and scripts with the project's own formatter, never generated diagram HTML ([publishing](publishing.md) "Where artifacts live"), and run the project's checks before committing. Project rules beat tool habits: when the project forbids heredocs, write the commit message to a file and commit with `git commit -F <file>`.
